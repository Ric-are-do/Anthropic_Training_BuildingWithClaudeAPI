# Project Setup

> **Key Insight — Server vs Client in Practice**
>
> In a real project you would only implement **one side**:
>
> - Building a **server only** — you're done once the tools, resources, and prompts are registered. Ship it and let others connect to it.
> - Building a **client only** — you skip the server entirely and point your `MCPClient` at an existing server (e.g. GitHub's MCP server). All their pre-built tools become available to Claude without you writing a single tool definition.
>
> In this project we're building both sides purely to understand how they communicate with each other.

We're going to build a CLI-based chatbot to better understand how MCP clients and servers work together. This hands-on project will give you practical experience with both sides of the MCP architecture.

## What We're Building

Our chatbot will allow users to interact with a collection of documents through a command-line interface. The system consists of two main components:

- An MCP client that handles user interactions
- A custom MCP server that manages document operations

The server will provide two essential tools: one for reading document contents and another for updating them. All documents will be stored in memory for simplicity - no database required.

> **Note — Educational Setup Only**
>
> In real-world projects, you typically implement either an MCP client or an MCP server, not both. You might create:
>
> - An MCP server to expose your service to other developers
> - An MCP client to connect to existing MCP servers
>
> We're building both components in this project purely for educational purposes - to understand how they communicate and work together.

## Your Server vs the MCP Server — What's the Difference?

In a normal app you have two parties: your server and Claude. Your server calls the Anthropic API and that's it.

With MCP there are **three parties**, and your server sits in the middle:

```
Your Server (mcp-chat.ts)
        ↕  Anthropic API
      Claude
        ↕  tool calls
Your Server (mcp-chat.ts)
        ↕  MCP protocol (stdio)
MCP Server (mcp-server.ts)
```

| | Your Server | MCP Server |
|---|---|---|
| What it is | The app you write — handles user input, calls Claude | A separate process that owns tools and data |
| Who calls it | The user / your code | Your server, on Claude's behalf |
| Knows about Claude? | Yes — it calls the Anthropic API | No — it only knows about documents |
| Knows about tools? | No — it just passes them to Claude | Yes — it defines and executes them |

**The flow in plain English:**

1. User types a question
2. Your server asks the MCP server "what tools do you have?"
3. Your server sends Claude the question plus the tools list
4. Claude says "I need to call `read_document`"
5. Your server receives that and calls `read_document` on the MCP server
6. The MCP server runs the function and returns the result
7. Your server sends that result back to Claude
8. Claude gives the final answer

Claude never directly touches the MCP server — your server is always the go-between.

**So what is the client then?**

The client (`mcp-client.ts`) is not a separate app or process — it lives inside your server. It's just the connector piece that knows how to speak the MCP protocol. Think of it like `HttpClient` in C# — you don't think of `HttpClient` as a separate server, it's just the object you use inside your app to talk to something external. `MCPClient` is the same idea, except instead of speaking HTTP it speaks MCP.

```
Your Server (mcp-chat.ts)
    └── uses MCPClient to talk to the MCP server
            ↕  MCP protocol (stdio)
        MCP Server (mcp-server.ts)
```

| Part | What it is |
|---|---|
| `mcp-chat.ts` | Your app — handles user input, drives the conversation |
| `mcp-client.ts` | A class inside your app — handles MCP communication |
| `mcp-server.ts` | A separate process — owns the tools and documents |

The client and your server are on the same side. The MCP server is the thing on the other side.

**Why bother separating them?**

Because in the real world the MCP server is usually something someone else built — GitHub's MCP server, AWS's MCP server, a database MCP server. You just connect your app to it and instantly have all their tools available without writing a single tool definition yourself. That's the whole point from lesson 1.

In this project we're building both sides ourselves so you can see exactly what's happening on each end.

```
mcp/
  mcp-server.ts    ← the MCP server — defines tools, resources, and prompts

Run the project with:

```

## How the Three Files Work Together

### mcp-server.ts — The MCP Server

This is the server Claude's tools live on. It holds an in-memory `docs` dictionary of six documents keyed by filename. It exposes:

- **Tools** — functions Claude can call during a conversation (read a doc, edit a doc)
- **Resources** — data endpoints the client can fetch directly without involving Claude (list all doc IDs, get a specific doc's content)
- **Prompts** — pre-built message templates the client can retrieve and inject into the conversation (summarize a doc, rewrite a doc in markdown)

The server communicates over **stdio** — it runs as a child process and speaks the MCP protocol over standard input/output. This is why `StdioServerTransport` is used.

```
mcp-server.ts  →  spawned as a child process  →  communicates via stdin/stdout
```

---

### mcp-client.ts — The MCP Client

`MCPClient` is a TypeScript class that wraps the MCP SDK's `Client`. It spawns the server as a child process and opens a stdio connection to it. Every method on `MCPClient` is a thin wrapper around an SDK call:

| Method | What it does |
|---|---|
| `connect()` | Spawns the server process and performs the MCP handshake |
| `listTools()` | Asks the server what tools are available |
| `callTool()` | Tells the server to run a specific tool with given arguments |
| `listPrompts()` | Asks the server what prompts are available |
| `getPrompt()` | Fetches a specific prompt with filled-in arguments |
| `readResource()` | Fetches a resource by URI (e.g. the doc list or a specific doc) |

The client does not talk to Claude — it only talks to the server. Claude never sees the MCP protocol directly.

---

### mcp-chat.ts — The Entry Point

This is where everything connects. It:

1. Creates an `MCPClient` and connects it to the server
2. Starts a `readline` loop to accept user input
3. For each message, calls `chat()` which handles two special input patterns before sending to Claude:

**`@doc_id` mentions** — if the user types `@report.pdf` in their message, the client calls `readResource("docs://documents/report.pdf")` and injects the document content directly into the prompt as `<document>` XML tags. Claude receives the content without needing to call a tool.

**`/command doc_id`** — if the user types `/summarize plan.md`, the client calls `getPrompt("summarize", { doc_id: "plan.md" })` and adds the returned message template straight into the conversation history. This lets the server define reusable prompt patterns.

For all other queries, the message goes to Claude with the full tools list. If Claude decides to call a tool (e.g. `read_document` or `edit_document`), the agentic loop handles it:

```
user input
  → build messages array
  → send to Claude with tools
  → if stop_reason === "tool_use":
      → call the tool via MCPClient
      → push tool result back into messages
      → send to Claude again
  → repeat until stop_reason === "end_turn"
  → return final text response
```

## The Two Ways to Get Document Content

This project uses two different mechanisms to surface document content to Claude, and understanding the difference is one of the key learning points:

| Mechanism | How | When to use |
|---|---|---|
| `@mention` → `readResource` | Client fetches content directly and injects it into the prompt | You know upfront which doc is needed — no tool call required |
| Tool use → `read_document` | Claude decides to call the tool itself during the conversation | Claude figures out it needs the doc mid-conversation |

The `@mention` approach is more efficient — it skips a round trip to Claude. The tool approach is more flexible — Claude can decide to read a document on its own if the user's question implies it needs one.

## Transport: Why stdio?

The server and client communicate over **stdio** (standard input/output) rather than HTTP. This means:

- The client spawns the server as a child process
- Messages flow over the process's stdin and stdout pipes
- No network port is needed — everything runs locally in the same machine

This is the simplest MCP transport and is typical for local development and educational projects. In production you would more likely use an HTTP/SSE transport so the server can run independently and serve multiple clients.
