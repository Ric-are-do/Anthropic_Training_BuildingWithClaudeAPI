# Implementing the MCP Client

## What is the Client and Why Do We Need It?

The MCP client is the piece of code that lives inside your application and knows how to talk to an MCP server. It handles the connection, sends requests, and receives responses — all using the MCP protocol under the hood.

Without the client, your application has no way to reach the server's tools. Claude never talks to the MCP server directly — your client is always the go-between.

---

## How It Fits Into the Grand Scheme

```
User
  └─→ Your App (mcp-chat.ts)
          ├─→ Anthropic API ──→ Claude
          └─→ MCPClient (mcp-client.ts)
                  └─→ MCP Server (GitHub / your own / anyone's)
                          └─→ Tools, Resources, Prompts
```

Think about the GitHub example. GitHub provides an MCP server with hundreds of pre-built tools — list repos, open pull requests, read issues, and more. If you were building a chatbot that answers questions about GitHub data, you would:

1. **Not touch the server** — GitHub already built and hosts it
2. **Only implement the client** — point your `MCPClient` at GitHub's server
3. **Pass the tools to Claude** — Claude sees all of GitHub's tools and can call them

Your application becomes the bridge between the user, Claude, and the MCP server. The client is what makes that bridge possible.

---

## The Two Components of an MCP Client

The MCP client consists of two main parts:

**1. The Client Session** — the actual connection to the server, provided by the MCP SDK. It handles the low-level protocol communication (handshake, message formatting, etc). It also requires proper resource cleanup when you're done with it — connections need to be closed correctly to avoid dangling processes.

**2. Your Custom MCPClient Class** — a wrapper class you write around the session to make it easier to use in your application. It handles the cleanup automatically and exposes simple methods like `listTools()` and `callTool()` so the rest of your app doesn't need to know anything about the MCP protocol.

In our project this is `mcp-client.ts`:

```typescript
export class MCPClient {
    private client: Client;        // the SDK session
    private transport: StdioClientTransport;  // the connection mechanism

    async connect(): Promise<void> { ... }    // opens the connection
    async disconnect(): Promise<void> { ... } // cleans up when done
    async listTools(): Promise<Tool[]> { ... }
    async callTool(...): Promise<unknown> { ... }
    ...
}
```

The reason we wrap the session in a class is resource management — the session needs to be properly closed when the app shuts down. The class handles that in one place so nothing leaks.

## How the Client Fits Into Our Application Flow

Our CLI chatbot needs to do two main things with the MCP server:

1. **Get a list of available tools** — so Claude knows what it can call
2. **Execute tools when Claude requests them** — so the actual work gets done

The `MCPClient` provides both of these through simple method calls:

```
User types a message
    → mcp-chat.ts calls mcpClient.listTools()
    → tools list is passed to Claude along with the message
    → Claude responds with stop_reason: "tool_use"
    → mcp-chat.ts calls mcpClient.callTool(name, input)
    → result is sent back to Claude
    → Claude gives the final answer
```

Without `listTools()`, Claude sees no tools and can't call any. Without `callTool()`, Claude can request a tool but nothing actually runs. Both methods need to be implemented for the full flow to work.

---

## What We Need to Implement

In `mcp-client.ts` the connection is already wired up. What's left are the five TODO methods:

| Method | Purpose |
|---|---|
| `listTools()` | Returns all tools the server has registered |
| `callTool()` | Executes a specific tool by name with given arguments |
| `listPrompts()` | Returns all prompts the server has registered |
| `getPrompt()` | Fetches a specific prompt with filled-in arguments |
| `readResource()` | Fetches a resource by URI (doc list or specific doc content) |

Each one is a thin wrapper around the MCP SDK's `this.client` methods — the SDK already knows how to talk to the server, we just need to call it and return the right data.

---

## The MCPClient Class — Brief Overview

`MCPClient` is a class that wraps the MCP SDK's built-in `Client`. The SDK `Client` already has all the protocol methods built in — your class just calls them and returns the data in a convenient shape for the rest of the app.

```typescript
export class MCPClient {
    private client: Client;               // the MCP SDK client — has all protocol methods
    private transport: StdioClientTransport; // spawns the server process and connects via stdio

    constructor(command: string, args: string[]) {
        this.transport = new StdioClientTransport({ command, args }); // tells it how to spawn the server
        this.client = new Client({ name: "mcp-chat-client", version: "1.0.0" });
    }

    async connect(): Promise<void> {
        await this.client.connect(this.transport); // performs the MCP handshake
    }

    async disconnect(): Promise<void> {
        await this.transport.close(); // cleans up the server process when done
    }
}
```

The class is responsible for two things: opening the connection cleanly and closing it cleanly. Everything in between is delegated to the SDK's `this.client`.

---

## Implementing `listTools()`

`listTools()` asks the server what tools are registered and returns them so they can be passed to Claude.

```typescript
async listTools(): Promise<Tool[]> {
    const result = await this.client.listTools();
    return result.tools;
}
```

- `this.client.listTools()` sends the request to the connected MCP server
- The SDK returns `{ tools: Tool[] }` — we pull out just the `tools` array
- These get passed to Claude on every message so Claude knows what it can call

You don't need to tell `this.client` which server to send the request to — it already knows because you called `connect()` when the app started. It's like calling a method on an `HttpClient` in C# where the base URL is already configured.

---

## Implementing `callTool()`

`callTool()` executes a specific tool on the server when Claude requests it.

```typescript
async callTool(name: string, input: Record<string, string>): Promise<unknown> {
    const result = await this.client.callTool({ name, arguments: input });
    return result;
}
```

- `name` is the tool Claude wants to call (e.g. `"read_document"`)
- `input` is the arguments Claude provided (e.g. `{ doc_id: "report.pdf" }`)
- The SDK packages these into the MCP protocol format and sends them to the server
- The server runs the tool function and sends the result back

Together `listTools()` and `callTool()` are the two core methods that make the full chat flow work. Everything else (`listPrompts`, `getPrompt`, `readResource`) builds on top of this foundation for the more advanced features.

## Testing the Client

Unlike the server which can be tested with the MCP Inspector, the client needs to be tested by actually connecting to the server and calling methods. The simplest way to do this is to add a `main()` function at the bottom of `mcp-client.ts`:

```typescript
async function main() {
    const client = new MCPClient("npx", ["tsx", "mcp/mcp-server.ts"]);
    await client.connect();

    const tools = await client.listTools();
    console.log("Available tools:", tools.map(t => t.name));

    await client.disconnect();
}

main();
```

Run it with:

```bash
npx tsx mcp/mcp-client.ts
```

This spawns the server, connects to it, calls `listTools()`, prints the tool names, and disconnects cleanly. You can extend it to test `callTool()` as well:

```typescript
const result = await client.callTool("read_document", { doc_id: "report.pdf" });
console.log("Tool result:", result);
```

This is useful for verifying your client methods are working in isolation before wiring everything up to Claude and the full chat loop.
