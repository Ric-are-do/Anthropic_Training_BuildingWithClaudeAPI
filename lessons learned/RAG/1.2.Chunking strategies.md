# Chunking Strategies

Chunking is the process of breaking a document into smaller pieces before storing or searching them. The strategy you choose affects how well Claude can answer questions — bad chunks mean missing context or irrelevant noise.

---

## 1. Size-Based Chunking

The simplest approach. You divide your text into strings of equal length. If you have a 325-character document, you might split it into three chunks of roughly 108 characters each.

**Why it's common:** Easy to implement and works with any type of document regardless of structure or format.

**Downsides:**
- Words get cut off mid-sentence
- Chunks lose important context from surrounding text
- Section headers might be separated from their content

---

### Overlap Chunking

To address the downsides above, you can add **overlap** between chunks. Each chunk includes some characters from the neighboring chunks, providing better context and ensuring complete words and sentences.

**Example — no overlap:**
```
Chunk 1: "The quick brown fox ju"
Chunk 2: "mps over the lazy dog"
```

**Example — with overlap (e.g. 10 characters):**
```
Chunk 1: "The quick brown fox ju"
Chunk 2: "fox jumps over the lazy dog"
```

The second chunk now starts a few words back, so "jumps" is never orphaned from its subject. The overlap size is a tunable parameter — larger overlap means better context continuity but more repeated content sent to Claude.

---

## 2. Structure-Based Chunking

Instead of splitting by character count, you split by the document's own structure — headings, sections, or other markers. Each chunk maps to a meaningful unit of the document rather than an arbitrary slice of text.

For a markdown document you can split on `## ` — every time a new top-level section starts, that becomes a chunk boundary.

**Example using `report.md`:**

The document contains sections like:

```
## Executive Summary
This report synthesizes the key findings and ongoing research efforts across the
organization's diverse operational and R&D departments for the past fiscal year...
```

```
## Table of Contents
1. Executive Summary
2. Table of Contents
3. Methodology
...
```

Each `##` heading becomes its own chunk, so when a user asks "what were the cybersecurity findings?" you retrieve only the `## Section 10: Cybersecurity Analysis` chunk — not the entire 80-line report.

**TypeScript implementation:**

```typescript
function chunkBySection(documentText: string): string[] {
    return documentText.split(/\n## /);
}
```

This is the direct equivalent of the Python `re.split(r"\n## ", document_text)`. The regex `\n## ` matches every newline followed by a `##` heading marker, splitting the document at each section boundary.

**Why it's not always favored:**

This approach gives you the cleanest, most meaningful chunks because each one represents a complete section. However, it only works when you have guarantees about your document structure. Many real-world documents are plain text or PDFs without clear structural markers — no headings, no consistent formatting, nothing to split on. Size-based chunking works on anything; structure-based chunking only works when the document cooperates.

---

## 3. Sentence-Based Chunking

A practical middle ground. You split text into individual sentences using a regular expression, then group consecutive sentences into chunks with optional overlap between groups.

This works well for most prose documents because sentences are natural units of meaning — you never cut a thought in half the way size-based chunking can.

**TypeScript implementation:**

```typescript
function chunkBySentences(text: string, sentencesPerChunk: number, overlap: number): string[] {
    const sentences = text.match(/[^.!?]+[.!?]+/g) ?? [];
    const chunks: string[] = [];

    for (let i = 0; i < sentences.length; i += sentencesPerChunk - overlap) {
        const chunk = sentences.slice(i, i + sentencesPerChunk).join(" ");
        chunks.push(chunk);
    }

    return chunks;
}
```

The regex `/[^.!?]+[.!?]+/g` matches any run of characters that ends with a sentence terminator (`.`, `!`, or `?`). The `overlap` parameter works the same way as in size-based overlap chunking — stepping back by `overlap` sentences each iteration so consecutive chunks share some context.

---

## 4. Semantic-Based Chunking

The most sophisticated approach. You split text into sentences, then use natural language processing (NLP) to measure how related consecutive sentences are. Sentences with high similarity get grouped into the same chunk; a drop in similarity signals a new chunk boundary.

The result is chunks that align with actual topic shifts in the document rather than arbitrary boundaries.

**Why it's expensive:**

Every sentence needs to be converted into an embedding (a vector of numbers representing its meaning) and then compared against its neighbors. This requires either a local NLP model or an API call per sentence — meaning a large document can generate hundreds of embedding requests before you've even started querying.

**When it's worth it:**

When chunk quality is critical and document structure is unpredictable. Long-form articles, research papers, and transcripts benefit the most because topic shifts rarely align with sentence counts or headings.

---

## Choosing Your Strategy

Your choice depends entirely on your use case and document guarantees:

| Strategy | Best for | Downside |
|---|---|---|
| **Structure-based** | Documents you control (internal reports, markdown) | Breaks on unstructured documents |
| **Sentence-based** | Most prose — a solid middle ground | Sentences vary wildly in length |
| **Size-based** | Any content type including code — reliable fallback | Can cut across sentence and section boundaries |
| **Semantic-based** | Best chunk quality, unpredictable documents | Computationally expensive to implement |

**Size-based chunking with overlap** is the most common production choice. It's simple, reliable, and works with any document type regardless of formatting. While it won't always produce perfect chunks, it consistently produces reasonable ones that won't break your pipeline.

There is no single best chunking strategy. The right approach depends on your specific documents, use cases, and the trade-off you're willing to make between implementation complexity and chunk quality.
