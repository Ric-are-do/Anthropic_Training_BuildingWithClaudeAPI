# The Full RAG Flow

```
Source Document
      |
      v
[Step 1: Chunk]
      |
      v
[Step 2: Embed Chunks]  ──→  Save to embeddings.json
      |
      v
[Step 3: Store Vectors]
      |
      ·  (setup complete — steps above only run once)
      ·
      v
[Step 4: User Asks a Question]
      |
      v
[Step 5: Embed the Question]
      |
      v
[Step 6: Find Most Similar Chunk]
      |
      v
[Step 7: Send Chunk + Question to Claude]
      |
      v
     Answer
```

---

## Step 1: Chunk Your Source Text

Break the source document into manageable sections. For this example we use two sections from `report.md`:

- **Section 1: Medical Research** — "This year saw significant strides in our understanding of XDR-47, a 'bug' we have not seen before."
- **Section 2: Software Engineering** — "This division dedicated significant effort to studying various infection vectors in our distributed systems."

---

## Step 2: Generate Embeddings

Convert each chunk into a vector using an embedding model. To keep the math simple, imagine a perfect model that returns exactly two numbers — one representing how medical the text is, and one representing how software-related it is:

| Chunk | Raw Vector | Normalised Vector |
|---|---|---|
| Medical Research | [0.9, 0.3] | [0.944, 0.331] |
| Software Engineering | [0.3, 1.0] | [0.295, 0.955] |

**Normalisation** scales each vector so its total magnitude equals 1.0. The embedding API handles this automatically — you don't need to do the math yourself. It ensures vectors are fairly comparable regardless of text length.

---

## Step 3: Store in Vector Database

Store the embeddings somewhere they can be searched later. In this project that is `Rag_Documents/embeddings.json` — a simple JSON file that acts as our vector database. Each entry stores the original chunk text alongside its vector so we can retrieve the text once we find a match.

Production systems use dedicated vector databases (Pinecone, Supabase) that are optimised for searching thousands or millions of vectors efficiently.

---

## Step 4: Process the User Query

A user asks: *"I'm curious about the company. In particular, what did the software engineering dept do this year?"*

We run this question through the same embedding model. The question scores low on medical content and high on software content:

| | Raw Vector | Normalised Vector |
|---|---|---|
| User query | [0.1, 0.89] | [0.112, 0.993] |

---

## Step 5: Find the Most Similar Chunk

We compare the query vector against every stored chunk vector to find the closest match. The comparison method used is **cosine similarity** — it measures the angle between two vectors. Vectors pointing in a similar direction (similar meaning) have a high cosine similarity close to 1.0.

You will also see **cosine distance** in documentation — it is simply `1 - cosine similarity`:

| Comparison | Cosine Similarity | Cosine Distance |
|---|---|---|
| Query vs Medical Research | low | close to 1 (far apart) |
| Query vs Software Engineering | high | close to 0 (similar) |

The vector database returns the **Software Engineering** section as the closest match.

---

## Step 6: Build the Final Prompt and Send to Claude

Combine the user's original question with the retrieved chunk and send it to Claude:

```
Context:
"This division dedicated significant effort to studying various infection vectors
in our distributed systems."

Question:
"What did the software engineering dept do this year?"
```

Claude reads only the relevant chunk — not the entire document — and generates a focused answer. This is the core value of RAG: Claude always receives the right context, at the lowest possible cost.
