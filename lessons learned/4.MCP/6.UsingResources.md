# Using Resources

## Testing Resources with the Inspector

The TypeScript equivalent of `uv run mcp dev mcp_server.py` is:

```bash
npx @modelcontextprotocol/inspector npx tsx mcp/mcp-server.ts
```

This spins up the MCP inspector and connects it to your server. Navigate to the **Resources** section to verify your resources are registered correctly. You can:

- Click **List Resources** to see `list_documents` and `fetch_document`
- Click a resource and provide a URI to test it — e.g. `docs://documents/report.pdf` to test the dynamic resource

---

## What We're Implementing

We're adding two resources to `mcp-server.ts` that power the `@mention` feature in the chat:

1. `docs://documents` — returns a list of all available document IDs
2. `docs://documents/{doc_id}` — returns the content of a specific document

When the user types `@report.pdf` in the chat, the client fetches the second resource and injects the document content directly into the prompt before Claude even sees the message.

---

## Resources vs Tools — The Key Distinction

This is an important distinction to understand:

| | Tools | Resources |
|---|---|---|
| Who calls them | Claude — during a conversation when it decides it needs to | The client — directly, before or outside of Claude |
| How they're triggered | Claude returns `stop_reason: "tool_use"` | Your code calls `readResource()` explicitly |
| Use case | Dynamic actions Claude decides to take | Fetching known data to inject into the prompt |

**Tools are Claude-driven. Resources are client-driven.**

In our project the `@mention` feature is powered by resources — when you type `@report.pdf`, the client calls `readResource("docs://documents/report.pdf")` and injects the content into the prompt as a `<document>` block. Claude never had to decide to fetch it — your code did it upfront.

The `read_document` tool is the alternative — Claude calls it mid-conversation when it decides on its own that it needs to read a doc. Less efficient but more flexible.

## Two Types of Resources

### Static Resource — Fixed URI

A static resource has a fixed URI with no variables. Used for things like listing all available documents.

```typescript
server.registerResource(
    "list_documents",             // name
    "docs://documents",           // fixed URI
    { mimeType: "application/json" },
    async (uri) => {
        return {
            contents: [{ uri: uri.href, text: JSON.stringify(Object.keys(docs)) }]
        };
    }
);
```

- The URI is a plain string — no variables
- `Object.keys(docs)` returns all the keys from the docs record as an array
- `JSON.stringify()` converts that array to a JSON string for the response
- `uri.href` is just the full URI string passed back so the client knows what it received

---

### Dynamic Resource — URI Template

A dynamic resource has a variable in the URI (like a URL parameter in a REST API). Used for fetching a specific document by ID.

```typescript
import { ResourceTemplate } from "@modelcontextprotocol/sdk/server/mcp.js";

server.registerResource(
    "fetch_document",
    new ResourceTemplate("docs://documents/{doc_id}", { list: undefined }),
    { mimeType: "text/plain" },
    async (uri, { doc_id }) => {
        return {
            contents: [{ uri: uri.href, text: docs[doc_id] }]
        };
    }
);
```

- `{doc_id}` in the URI template is the variable — it gets extracted from the URI automatically
- The SDK passes it as the second argument to your handler `({ doc_id })`
- `{ list: undefined }` tells the SDK this resource doesn't support listing all instances
- `mimeType: "text/plain"` because we're returning raw document text, not JSON
- `ResourceTemplate` must be imported from `@modelcontextprotocol/sdk/server/mcp.js`
- Check if the doc exists before returning, same as the tool — return an error if not found

## The URI Is a Reference, Not a Location

The URI like `docs://documents` is **not** a real network address you can visit in a browser. It's just an identifier the MCP protocol uses internally to route requests to the right handler. Think of it like a key in a dictionary:

```
"docs://documents"             → listDocs handler
"docs://documents/report.pdf"  → fetchDoc handler
```

The `docs://` part looks like a URL scheme but has no network meaning — you made it up. You could call it `banana://documents` and it would work exactly the same. It's just a string the client and server agree on so they can refer to the same resource.

The URI serves two purposes:
1. **The MCP protocol requires it** — `readResource()` needs something to identify which resource it wants. Without it there's no way to route the request to the right handler.
2. **It distinguishes between resources** — when you have multiple resources registered, the URI is what tells the server which one you want.

## `content` vs `contents`

These look similar but are used in different places and have different shapes — easy to mix up:

| | `content` | `contents` |
|---|---|---|
| Used in | **Tool** responses | **Resource** responses |
| Item shape | `{ type: "text", text: "..." }` | `{ uri: "...", text: "..." }` |

```typescript
// Tool return shape — uses "content"
return { content: [{ type: "text", text: "result here" }] }

// Resource return shape — uses "contents"
return { contents: [{ uri: uri.href, text: "result here" }] }
```

The MCP protocol defines them differently by design — tools return content blocks, resources return resource contents. The SDK will complain if you use the wrong one.

---

## MIME Types

Resources can return any type of data — strings, JSON, binary, etc. The `mimeType` property in the config object gives clients a hint about what kind of data you're returning:

| MIME Type | Use case |
|---|---|
| `application/json` | Structured JSON data (e.g. a list of document IDs) |
| `text/plain` | Plain text content (e.g. the raw content of a document) |

In TypeScript you need to manually serialize your data before returning it — the SDK does not do this for you. That's why we use `JSON.stringify()` when returning the document list:

```typescript
// returning a list — must manually stringify
text: JSON.stringify(Object.keys(docs))  // → '["deposition.md","report.pdf",...]'

// returning plain text — no conversion needed
text: docs[doc_id]!  // → "This deposition covers the testimony of..."
```

The `mimeType` you set should match what you're actually returning — it tells the client how to parse the `text` field it receives.

## Implementing `readResource()` in the Client

This is the client-side method that fetches a resource from the server. Here's the full implementation with comments:

```typescript
async readResource(uri: string): Promise<unknown> {
    // 1. Send the URI to the MCP server over the active session
    //    The server matches the URI to the right handler and runs it
    //    e.g. "docs://documents" → listDocs handler
    //         "docs://documents/report.pdf" → fetchDoc handler
    const result = await this.client.readResource({ uri });

    // 2. The server returns a contents array — grab the first item
    //    Each item is either a text resource { uri, text } or blob resource { uri, blob }
    const firstContent = result.contents[0];

    // 3. Guard — if contents was empty, return null
    if (!firstContent) return null;

    // 4. Guard — narrow the type to text resource (not blob)
    //    TypeScript sees contents as text | blob, this confirms it has a text field
    if (!("text" in firstContent)) return null;

    // 5. List resource — text is a JSON string e.g. '["deposition.md","report.pdf"]'
    //    Parse it back into an actual array before returning
    if (uri === "docs://documents") {
        return JSON.parse(firstContent.text as string);
    }

    // 6. Single doc resource — text is plain string, return it directly
    return firstContent.text;
}
```

## How `readResource()` Flows Through the System

```
mcp-chat.ts
  │
  │  user types "@report.pdf"
  │
  ▼
mcpClient.readResource("docs://documents/report.pdf")
  │
  │  sends { uri: "docs://documents/report.pdf" } over stdio session
  │
  ▼
mcp-server.ts
  │
  │  matches URI to fetch_document handler
  │  extracts doc_id = "report.pdf" from the URI template
  │  looks up docs["report.pdf"]
  │  returns { contents: [{ uri: "docs://documents/report.pdf", text: "The report details..." }] }
  │
  ▼
mcpClient.readResource() receives result
  │
  │  grabs result.contents[0]
  │  confirms it has a "text" field (not blob)
  │  checks firstContent.mimeType:
  │    → "application/json" : parses text as JSON and returns an array/object
  │    → "text/plain"       : returns text directly as a plain string
  │
  ▼
mcp-chat.ts
  │
  │  injects content into the prompt as:
  │  <document id="report.pdf">
  │    The report details the state of a 20m condenser tower.
  │  </document>
  │
  ▼
Claude receives the message with the document content already embedded
No tool call needed — the content is already there
```

## Python vs TypeScript — Two Approaches to Parsing Resource Responses

The Python version uses the **MIME type** to decide how to parse the response:

```python
async def read_resource(self, uri: str) -> Any:
    result = await self.session().read_resource(AnyUrl(uri))
    resource = result.contents[0]

    if isinstance(resource, types.TextResourceContents):
        if resource.mimeType == "application/json":
            return json.loads(resource.text)  # parse JSON string into a Python object
        return resource.text                  # return plain text directly
```

Our TypeScript version uses the **URI** to decide how to parse:

```typescript
if (uri === "docs://documents") {
    return JSON.parse(firstContent.text as string); // parse JSON string into an array
}
return firstContent.text; // return plain text directly
```

**Which approach is better?**

The MIME type approach is cleaner — it doesn't hardcode a specific URI so it works for any resource that returns JSON, not just `docs://documents`. If you added a new JSON resource with a different URI, the Python version would handle it automatically. The TypeScript version would need an extra `if` check.

A more robust TypeScript version using MIME type would look like:

```typescript
async readResource(uri: string): Promise<unknown> {
    const result = await this.client.readResource({ uri });
    const firstContent = result.contents[0];

    if (!firstContent) return null;
    if (!("text" in firstContent)) return null;

    if (firstContent.mimeType === "application/json") {
        return JSON.parse(firstContent.text as string);
    }
    return firstContent.text;
}
```

Both work for our project — the URI check is simpler to understand when learning, the MIME type check is better practice for production code.

---

## The Return Shape

Both resource types return the same shape:

```typescript
return {
    contents: [{ uri: uri.href, text: "your data here" }]
}
```

The `contents` array can hold multiple items but for document resources a single item is all you need. The `uri.href` is passed back so the client knows which resource it received.
