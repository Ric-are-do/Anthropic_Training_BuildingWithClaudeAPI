# Defining Tools with MCP

Tools are functions that Claude can call during a conversation when it decides it needs to perform an action or look something up. In MCP, tools are defined on the server and automatically made available to Claude through the client.

---

## How Tools Fit Into MCP

When `mcp-chat.ts` starts up, it calls `mcpClient.listTools()` which asks the MCP server "what tools do you have?". The server returns all registered tools including their names, descriptions, and input schemas. These get passed to Claude on every message so Claude knows what it can call.

When Claude decides to use a tool, it returns `stop_reason: "tool_use"` and your server calls `mcpClient.callTool()`, which tells the MCP server to actually execute the function. Claude never runs the function itself — it just requests it.

---

## Registering a Tool — `server.registerTool()`

In our project we use `server.registerTool()` from the `@modelcontextprotocol/sdk`. Note that the older `server.tool()` method still works but is **deprecated** — the IDE will show a strikethrough on it. Always use `registerTool()`.

```typescript
server.registerTool(
    "read_document",           // 1. tool name
    {
        description: "...",    // 2. what the tool does (Claude reads this)
        inputSchema: { ... }   // 3. the parameters the tool accepts
    },
    async ({ doc_id }) => {    // 4. the function that runs when Claude calls it
        ...
        return { content: [{ type: "text", text: "..." }] }
    }
);
```

### The Four Parts

**1. Name** — a string identifier Claude uses to request this tool. Keep it snake_case and descriptive.

**2. Description** — a plain English explanation of what the tool does. Claude reads this to decide whether to call the tool. A good description helps Claude choose the right tool at the right time.

**3. inputSchema** — defines the parameters the tool accepts, using Zod. Every field in the schema becomes a parameter Claude must provide when calling the tool.

**4. Handler function** — the async function that actually runs. It receives the validated input and must return `{ content: [{ type: "text", text: "..." }] }`.

---

## Input Schemas with Zod

Zod is a schema validation library. It validates that Claude's input matches what you expect before your function runs.

```typescript
inputSchema: {
    doc_id: z.string().describe("The filename of the document, e.g. report.pdf")
}
```

Each field in the schema has three things:

| Part | Example | What it does |
|---|---|---|
| Parameter name | `doc_id` | The name Claude uses when calling the tool |
| Zod type | `z.string()` | Validates the input is the right type |
| `.describe()` | `"The filename..."` | Tells Claude what this parameter is for |

The `.describe()` is important — it gets sent to Claude as part of the tool definition so Claude knows what value to pass in. Without it Claude has to guess.

This is the same concept as the manual tool schemas you wrote in `Tools/ToolsHandler.ts`, just expressed more cleanly:

```typescript
// Old manual way — schema and function defined separately
{
    name: "read_document",
    input_schema: {
        type: "object",
        properties: {
            doc_id: { type: "string", description: "The filename of the document" }
        }
    }
}

// MCP + Zod way — schema and function in one call
server.registerTool("read_document", {
    inputSchema: { doc_id: z.string().describe("The filename of the document") }
}, async ({ doc_id }) => { ... })
```

## The Return Shape

Every tool handler must return this shape:

```typescript
return { content: [{ type: "text", text: "your result here" }] }
```

The `content` array can hold multiple items but for most tools a single text item is all you need.

---

## The `read_document` Tool

```typescript
server.registerTool(
    "read_document",
    {
        description: "Reads the content of a document",
        inputSchema: {
            doc_id: z.string().describe("The id of the document to read")
        }
    },
    async ({ doc_id }) => {

        // Check the doc exists before trying to return it.
        // docs[doc_id] returns string | undefined so we guard with 'in' first.
        if (!(doc_id in docs)) {
            return { content: [{ type: "text", text: `Error: Document with id ${doc_id} not found.` }] }
        }

        // The ! (non-null assertion) tells TypeScript we've already confirmed
        // the key exists above, so docs[doc_id] cannot be undefined here.
        return { content: [{ type: "text", text: docs[doc_id]! }] }
    }
);
```

### Why `!(doc_id in docs)` instead of `if (docs[doc_id])`?

The `in` operator checks whether the key exists in the object. `docs[doc_id]` returns `string | undefined` because TypeScript can't guarantee the key exists at compile time. Using `in` satisfies TypeScript's type checker and avoids the `undefined` warning.

### Why the `!` on `docs[doc_id]`?

Even after the `if` guard, TypeScript still considers `docs[doc_id]` to be `string | undefined` because it doesn't track that the `in` check already proved the key exists. The `!` non-null assertion tells TypeScript "trust me, this won't be undefined here." It's safe to use because we've already guarded above.

## Reading the Method Structure

`registerTool` takes three arguments separated by commas:

```typescript
server.registerTool(
    "read_document",         // argument 1 — name
    { ... },                 // argument 2 — config object, ends with closing }
    async ({ doc_id }) => {  // argument 3 — the function, starts here
        ...
    }                        // function body ends here
);                           // registerTool call ends here
```

The third argument is the entire `async ({ doc_id }) => { ... }` block. It's just a value being passed in — the same way you'd pass a string or number, except you're passing a function.

## Why `async ({ doc_id }) => { }` Instead of a Named Function?

In `Tools/ToolsHandler.ts` you defined functions separately and then referenced them by name:

```typescript
// defined separately
function getCurrentDateTime() { ... }

// referenced by name
const toolsHandler = { getCurrentDateTime }
```

Here you're passing the function directly as an argument — called an **anonymous arrow function**. Both approaches are equivalent:

```typescript
// anonymous — defined inline, only used in one place
server.registerTool("read_document", { ... }, async ({ doc_id }) => {
    ...
});

// named — defined separately, passed by reference
async function readDocument({ doc_id }: { doc_id: string }) {
    ...
}
server.registerTool("read_document", { ... }, readDocument);
```

The inline style is more common when the function is short and only used in one place — no point giving it a name if nothing else needs to reference it.

The `async` is there because the handler might eventually do async work (like reading from a database). It doesn't hurt to have it even when the function body is currently synchronous.
