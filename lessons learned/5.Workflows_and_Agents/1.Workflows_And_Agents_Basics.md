# Workflows and Agents Basics

Workflows and agents are strategies for handling user tasks that can't be completed by Claude in a single request. You've actually been creating both throughout this course — when you used tools and let Claude figure out how to complete tasks, that was an agent.

---

## When to Use Workflows vs Agents

The decision comes down to how well you understand the task:

- **Use workflows** when you can picture the exact flow or steps that Claude should go through to solve a problem, or when your app's UX constrains users to a set of tasks
- **Use agents** when you're not sure exactly what task or task parameters you'll give to Claude

**Workflows** are a series of calls to Claude meant to solve a specific problem through a predetermined series of steps.

**Agents** give Claude a goal and a set of tools, expecting Claude to figure out how to complete the goal through the provided tools.

---

## Example: Image to CAD Workflow

A good way to understand workflows is through a concrete example. Imagine building a web app where users drag and drop an image of a metal part, and you need to generate a STEP file (an industry standard for 3D models) from it.

Since we have a clear picture of exactly what steps to follow when a user supplies an image, this makes a perfect workflow candidate — we can write the entire flow out as a predefined series of steps:

```
Step 1: Feed the image into Claude
        → Ask Claude to describe the object in the image

Step 2: Generate the model
        → Based on the description, ask Claude to use the CadQuery
          library to write code that models the object

Step 3: Create a rendering
        → Run the generated CadQuery code to produce a 3D rendering

Step 4: Grade the rendering
        → Ask Claude to compare the rendering against the original image
        → If issues are found, send feedback back to Step 2 and repeat
        → If accepted, output the final STEP file
```

Each step is a separate call to Claude with a specific, known purpose. Claude doesn't decide what to do next — your code does.

---

## The Evaluator-Optimizer Pattern

The CAD workflow above is an example of a well-known pattern called the **Evaluator-Optimizer**. Here's how it works:

| Role | Responsibility |
|---|---|
| **Producer** | Takes input and creates output (Claude using CadQuery to model the part) |
| **Grader** | Evaluates the output against some criteria (Claude comparing the rendering to the image) |
| **Feedback loop** | If the grader rejects the output, feedback goes back to the producer |
| **Iteration** | The cycle repeats until the grader accepts the output |

```
Input
  └─→ Producer (Claude generates output)
          └─→ Grader (Claude evaluates output)
                ├─→ Accepted → final output
                └─→ Rejected → feedback → Producer (try again)
```

This pattern is powerful because it mimics a human review cycle — produce something, check it, improve it, repeat.

---

## Why Learn Workflow Patterns

The goal of identifying different workflow patterns is to give you a set of repeatable recipes for implementing your own features. The Evaluator-Optimizer is one pattern that has worked well for many engineers — consider using it in your own app.

Keep in mind: identifying a workflow pattern doesn't write the code for you. You still have to implement each step. But having a named pattern to reach for makes it much easier to design the solution before you start coding.
