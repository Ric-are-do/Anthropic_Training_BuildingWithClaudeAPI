# Workflow Parallelization

When building AI applications, you'll often encounter tasks that seem simple on the surface but become complex when you try to implement them effectively. The **parallelization workflow** pattern helps you break down complex tasks into manageable, focused pieces.

---

## The Problem with Complex Single Prompts

Imagine building a material designer application where users upload images of parts and receive recommendations for the best material to use. Your first instinct might be to send the image to Claude with a single prompt asking it to choose between metal, polymer, ceramic, composite, elastomer, or wood.

While this works, you're asking Claude to juggle a lot at once. Without specific criteria for each material type, results won't be as reliable as they could be.

You might then try adding detailed criteria for every material into one massive prompt — but this creates a new problem. Claude has to balance all those different considerations simultaneously, which can lead to confusion and suboptimal results.

```
Single prompt approach (problematic):

Image + "choose between metal, polymer, ceramic, composite, elastomer, wood"
  └─→ Claude tries to evaluate ALL criteria at once
          └─→ Less focused, less reliable results
```

---

## A Better Approach: Parallelization

Instead of cramming everything into one request, split the task into multiple parallel requests. Each request focuses on evaluating the part for a single material type with specialised criteria.

```
Parallelization approach:

                    ┌─→ Claude: evaluate for METAL     ─┐
                    ├─→ Claude: evaluate for POLYMER   ─┤
Image ─→ Split ────├─→ Claude: evaluate for CERAMIC   ─┼──→ Aggregate ─→ Final recommendation
                    ├─→ Claude: evaluate for COMPOSITE ─┤
                    ├─→ Claude: evaluate for ELASTOMER ─┤
                    └─→ Claude: evaluate for WOOD      ─┘

All 6 requests run simultaneously — not one after another
```

Each request gives Claude one job with specialised criteria. All requests run at the same time. The results are then collected and fed into a final aggregation step where Claude compares them and makes a recommendation.

---

## How Parallelization Workflows Work

The pattern follows three steps:

**1. Split** — Break the complex decision into focused, specialised sub-tasks

**2. Run in parallel** — Execute all sub-tasks simultaneously for faster processing

**3. Aggregate** — Combine the specialised results into a final decision

```
Step 1: Split
  Complex task → [sub-task A, sub-task B, sub-task C, ...]

Step 2: Run in parallel
  sub-task A ──→ result A ─┐
  sub-task B ──→ result B ─┼──→ Step 3: Aggregate ──→ Final output
  sub-task C ──→ result C ─┘
```

Note: the parallelised sub-tasks don't need to be identical — each can have a specialised prompt, its own set of tools, or different evaluation criteria.

---

## Benefits of This Approach

**Focused attention** — Claude concentrates on one specific aspect at a time rather than balancing multiple competing considerations. This leads to more thorough and accurate analysis for each material type.

**Easier optimisation** — You can improve and test the prompt for each material evaluation independently. If your metal analysis isn't working well, refine just that prompt without touching the others.

**Better scalability** — Adding a new material to evaluate is straightforward — just add another parallel request. You don't need to rewrite existing prompts or worry about interference.

**Improved reliability** — Breaking down the complex task reduces the cognitive load on the model and produces more consistent results.

---

## When to Use Parallelization

This pattern works well when you have a complex decision that can be broken into independent evaluations. Look for situations where you're asking Claude to:

- Consider multiple criteria simultaneously
- Compare several distinct options
- Make decisions that span different domains of expertise

The key is identifying tasks that can be **meaningfully separated** — each parallel sub-task should operate independently and contribute a distinct piece of analysis to the final decision.

If sub-tasks depend on each other's results, parallelization won't work — use a sequential workflow instead.
