# Text Embeddings

## What is a Text Embedding?

A text embedding is a numerical representation of the meaning contained in some text. Think of it as converting words and sentences into a format that computers can work with mathematically.

Rather than storing text as a string, an embedding stores it as a list of numbers — and those numbers capture the *meaning* of the text, not just the characters. This is what allows a computer to compare two pieces of text by how similar their meanings are, rather than just checking if the same words appear.

---

## How It Works

1. You feed text into an embedding model
2. The model outputs a long list of numbers (the embedding)
3. Each number ranges from -1 to +1
4. These numbers represent different qualities or features of the input text

The resulting list is called a **vector**. Two pieces of text that mean similar things will produce vectors that are mathematically close to each other. This is what powers semantic search — finding chunks that are *meaningfully* relevant to a question, not just chunks that share the same keywords.

---

## Embeddings and Claude

Anthropic does not provide an embeddings API. In a RAG pipeline, Claude handles the **generation** side — reading the retrieved chunks and producing an answer. A separate embeddings provider handles the **retrieval** side — finding which chunks are relevant to the question.

**Common third-party options:**

| Provider | Model | Notes |
|---|---|---|
| **OpenAI** | `text-embedding-3-small` | Fast and cheap, widely used |
| **Google** | `text-embedding-004` | Available via the Gemini API |
| **Cohere** | `embed-english-v3.0` | Built specifically for search use cases |
| **VoyageAI** | `voyage-3` | Strong performance on retrieval tasks |

**In this project we use VoyageAI.** The SDK is installed via `npm install voyageai` and the API key is stored as `VOYAGE_API_KEY` in the `.env` file.

## Where Embeddings Fit in a RAG Pipeline

1. Chunk the document using one of the chunking strategies
2. Pass each chunk through an embeddings model to get its vector
3. Store those vectors (in memory, or in a vector database like Pinecone or Supabase)
4. When a user asks a question, embed the question the same way
5. Find the chunks whose vectors are closest to the question vector
6. Pass those chunks to Claude as context for the final answer

**In this project**, the embeddings are saved to `Rag_Documents/embeddings.json`. Each entry contains the original chunk text and its vector. You can open that file directly to inspect the stored embeddings.

## Can I Just Ask ChatGPT to Embed My Text?

No — ChatGPT is a chat interface, not an embeddings API. Asking it to "embed text" would just get you a description of what embeddings are, not the actual numerical vectors.

To get real embeddings you need to call the API directly, the same way you call the Anthropic API:

```typescript
const response = await openai.embeddings.create({
    model: "text-embedding-3-small",
    input: "your text here"
});

const vector = response.data[0].embedding; // an array of ~1500 numbers
```

| | What it does |
|---|---|
| **ChatGPT** | Generates conversational text responses |
| **Embeddings API** | Returns a raw vector for a piece of text |

They are separate products that happen to be made by the same company. Same situation as Anthropic — Claude is the chat model, but Anthropic does not have an embeddings product at all.

## Does Embedding Happen Every Time the Script Runs?

It depends on how you build it.

**Without storing vectors (naive approach):**
Yes — every time you start the script you re-embed all chunks from scratch, which is slow and wastes API calls.

**The right approach — embed once, store, reuse:**
1. Run an embedding step **once** to embed all your chunks and save the vectors to a file (e.g. a JSON file or a vector database)
2. Every subsequent run just **loads** the saved vectors — no API calls needed
3. You only re-embed if the source document changes

```
First run:
  read document → chunk → embed each chunk → save vectors to file

Every run after:
  load vectors from file → embed the user's question → search
```

This is called a **pre-processing step** and is standard practice. For a small project with one document, saving to a JSON file is perfectly fine. Production systems use vector databases (Pinecone, Supabase) which are optimised specifically for storing and searching vectors at scale.

The key insight is: **documents don't change often, but questions do**. So you embed documents once upfront, and only embed the live user question on each run — which is just one API call per question.

## Managing VoyageAI Embedding in This Project

In `rag.ts` there is a flag at the top of the file that controls whether VoyageAI is called:

```typescript
const FORCE_REEMBED = false;
```

The script automatically checks whether `Rag_Documents/embeddings.json` already exists. Based on that and the flag, it decides what to do:

| Scenario | `FORCE_REEMBED` | embeddings.json exists | What happens |
|---|---|---|---|
| First time running | `false` | No | Calls VoyageAI, generates embeddings, saves to file |
| Normal run | `false` | Yes | Loads from file — no VoyageAI calls |
| New document added | `true` | Yes | Ignores existing file, re-embeds everything, overwrites file |

**When to set `FORCE_REEMBED = true`:**
- You added a new document to `Rag_Documents/`
- You changed the chunking strategy
- You want to use a different VoyageAI model

**When to leave it as `false`:**
- Every normal run where the document hasn't changed
- Any time you just want to test the search or generation side of the pipeline

Remember to set it back to `false` after re-embedding — leaving it as `true` will call VoyageAI on every single run and burn through your API quota.
