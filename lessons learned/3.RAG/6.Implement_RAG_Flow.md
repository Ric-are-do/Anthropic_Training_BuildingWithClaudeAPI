# Implementing the Full RAG Flow

This document explains how all the files in the RAG implementation connect together and what each one is responsible for.

---

## File Map

```
Rag_Documents/
  report.md              ← source document (what we search through)
  embeddings.json        ← saved vectors (generated once, reused every run)

utilities/Chunking/
  chunking.ts            ← functions that split a document into chunks
  embeddings.ts          ← calls VoyageAI to convert text into vectors
  vectorStore.ts         ← stores vectors in memory and searches them

rag.ts                   ← entry point — wires all five steps together
```

---

## How It All Connects — Step by Step

### Step 1: Chunk the Document (`chunking.ts`)

`rag.ts` reads `report.md` into a string and passes it to `chunkBySection()` from `chunking.ts`. This splits the document on every `##` markdown heading, giving us one chunk per section. `sections[0]` is just the document title so we skip it with `.slice(1)`.

```
report.md  →  chunkBySection()  →  sections[]
```

---

### Step 2: Generate Embeddings (`embeddings.ts`)

The sections array is passed to `generateEmbedding()` in `embeddings.ts`. This function sends all chunks to VoyageAI in a single batch call and gets back a 2D array — one vector per chunk. Each vector is a list of ~1024 numbers representing the meaning of that chunk.

This only runs if `embeddings.json` does not exist or `FORCE_REEMBED` is set to `true`. Otherwise the saved file is loaded instead, skipping all VoyageAI calls.

```
sections[]  →  generateEmbedding(sections, "document")  →  number[][]
```

---

### Step 3: Store in the Vector Index (`vectorStore.ts`)

The embeddings and their original text are loaded into a `VectorIndex` instance from `vectorStore.ts`. For each chunk we call `store.addVector(embedding, { content: text })`. The `content` field stores the original text so we can retrieve it after a search — without it, search results would just be numbers with no meaning.

```
embeddedChunks[]  →  store.addVector()  →  VectorIndex (in memory)
```

---

### Step 4: Embed the User's Question (`embeddings.ts`)

When the user asks a question, we pass it to `generateEmbedding()` again — this time as a single string with `inputType: "query"`. VoyageAI returns one vector representing the meaning of the question.

Using `"query"` instead of `"document"` is important — VoyageAI optimises the vector differently depending on whether the text is a question or a stored chunk.

```
userQuestion  →  generateEmbedding(question, "query")  →  number[]
```

---

### Step 5: Search the Vector Index (`vectorStore.ts`)

We call `store.search(queryEmbedding, 2)` to find the 2 most similar chunks. Internally `VectorIndex` calculates the **cosine distance** between the query vector and every stored vector. Cosine distance measures how different two vectors are in direction — values close to 0 mean similar meaning, values close to 1 mean very different.

Results are returned as `[metadata, distance]` pairs sorted from closest to furthest. We pull `metadata.content` out of each result to get the original text back.

```
queryEmbedding  →  store.search()  →  [{ content: text }, distance][]
```

---

## The `FORCE_REEMBED` Flag (`rag.ts`)

At the top of `rag.ts` there is a flag:

```typescript
const FORCE_REEMBED = false;
```

When `false` — the script checks if `embeddings.json` exists. If it does, it loads from file and skips VoyageAI entirely.
When `true` — the script ignores the saved file, re-embeds everything, and overwrites `embeddings.json`.

Set it to `true` only when you add a new document or change the chunking strategy. Set it back to `false` immediately after.

## Example Response

Below is a real example of the system running against `report.md`:

```
Loading embeddings from file...

Ready — 14 embedded chunks loaded.

Document loaded. Type a question or "exit" to quit.

Your question: tell me about the software engineering project

Top results:

Distance: 0.5439
Section 2: Software Engineering - Project Phoenix Stability Enhancements

The Software Engineering division dedicated considerable effort to improving the stability and performance of the core systems...

Distance: 0.5576
Executive Summary

This report synthesizes the key findings and ongoing research efforts across the organization's diverse operational and R&D departments for the past fiscal year. Our strength lies i...
```

**What this tells us:**

- The system correctly identified **Section 2: Software Engineering** as the most relevant chunk with a distance of `0.5439` — the lowest (most similar) score
- The **Executive Summary** came second at `0.5576` — slightly further away but still relevant since it mentions all departments including software engineering
- The embeddings were loaded from file rather than regenerated — no VoyageAI calls were needed for the document chunks, only for the user's question

**Why did the Executive Summary appear in the results?**

There are two reasons for this:

1. **The Executive Summary mentions every department** — including software engineering. When it was embedded, VoyageAI picked up on the software engineering content inside it, so its vector ends up pointing in a similar direction to the question. It is not the best match, but it is close enough to land in the top 2.

2. **We always return a fixed number of results** — the second slot will always be filled with whatever is second closest, even if it is not that relevant. The distance scores here are very close (`0.5439` vs `0.5576`), which shows the Executive Summary is only marginally less relevant than the actual section.

This is a limitation of structure-based chunking — the Executive Summary is one large chunk covering all 10 departments, so it competes with everything. A better approach would break it down further so each topic is more isolated.

In production RAG systems this is often addressed with a **relevance threshold** — only returning results whose distance is below a certain value, rather than always returning a fixed number of results regardless of how relevant they actually are.

## Full Data Flow Summary

```
report.md
  └─ chunkBySection()           [chunking.ts]
       └─ generateEmbedding()   [embeddings.ts]  ──→  embeddings.json (saved)
            └─ VectorIndex      [vectorStore.ts]
                 └─ search(queryEmbedding)
                      └─ top N chunks returned with cosine distance scores
```
